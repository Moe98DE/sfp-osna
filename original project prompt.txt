# Build a Static Instagram → Gemini → Website Publishing System

You are a senior full-stack engineer. Build this project completely, not merely a scaffold or architectural proposal.

The guiding priorities, in order, are:

1. Simplicity
2. Maintainability
3. Reliability
4. Functionality
5. Good SEO and machine readability
6. Visual polish

Avoid unnecessary abstractions, frameworks, services, databases, queues, containers, and infrastructure.

The finished website must be deployable as a completely static site to a host such as Neocities.

---

# 1. Project Goal

Build a small organization's public website.

The organization primarily publishes updates on Instagram.

The website should automatically detect new Instagram posts, retrieve their captions and media, use Google's Gemini API to turn them into richer web articles, store those articles locally as version-controlled content, rebuild the static website, and deploy it.

The conceptual pipeline is:

Instagram
→ official Meta API
→ sync script
→ download/optimize media
→ Gemini
→ validate structured response
→ generate local article
→ static site build
→ deploy

There must be no requirement for:

- a database
- an always-running backend
- a CMS
- browser-side API calls to Gemini or Instagram
- secrets in frontend JavaScript
- a persistent server process

GitHub Actions should be capable of running the entire publishing pipeline periodically.

# 5. Instagram Integration

Use the official Meta/Instagram API.

Do NOT scrape Instagram HTML.

Encapsulate Instagram-specific API code behind a small module.

The rest of the project should work with a simple internal representation similar to:

```ts
interface InstagramPost {
  id: string;
  permalink: string;
  caption: string;
  publishedAt: string;
  mediaType: "IMAGE" | "CAROUSEL" | "VIDEO" | "REEL" | "UNKNOWN";
  media: {
    url: string;
    type: "image" | "video";
  }[];
}
```

Adapt the actual Meta response into this representation.

Support at minimum:

- single image posts
- image carousel posts

Handle video/reel posts gracefully.

If robustly downloading video would complicate the MVP, generate an article using its available metadata/poster and link prominently to the original Instagram post rather than building an elaborate video pipeline.

The integration should:

- authenticate through environment variables
- never expose credentials to the frontend
- fetch recent posts
- fetch carousel children where required
- normalize results
- retry transient failures conservatively
- produce understandable errors
- respect API rate limits
- avoid unnecessary requests

Do not hardcode secrets.

Provide `.env.example`.

# 6. Idempotency

Synchronization MUST be safe to run repeatedly.

Running:

```bash
npm run sync
```

five times against the same Instagram account must not create five copies of an article.

Store the Instagram media ID in article frontmatter.

Before importing something, detect whether that media ID already exists.

Example:

```yaml
instagram:
  mediaId: "..."
  permalink: "..."
  publishedAt: "..."
```

Do not require a separate database merely to track processed IDs if the content repository itself can be the source of truth.

---

# 7. Never Destroy Human Edits

This requirement is important.

Once an article has been generated, a human may manually edit it.

Future Instagram syncs must NOT silently regenerate or overwrite that article.

Default behavior:

- existing Instagram media ID → skip
- new Instagram media ID → create

Provide an explicit force/regenerate mechanism only if it is simple and safe.

For example:

```bash
npm run sync -- --force <media-id>
```

but ordinary synchronization must preserve manual edits.

---

# 8. Media Handling

Do not permanently depend on Instagram CDN URLs.

When importing a post:

1. retrieve its image(s)
2. download them during the sync process
3. optimize them for the web
4. save them into the site's own static media directory
5. reference the local files from the generated article

Use deterministic paths, for example:

```text
public/media/posts/<instagram-id>/01.webp
public/media/posts/<instagram-id>/02.webp
```

Reasonable optimization targets:

- preserve useful visual quality
- avoid enormous originals
- constrain maximum dimensions
- use a modern web format where sensible
- preserve aspect ratio
- do not upscale small images

Keep implementation straightforward.

The website should use responsive image markup where practical.

# 9. Gemini Integration

Create a separate Gemini module.

The sync script should provide Gemini with:

1. the Instagram caption
2. publication timestamp
3. relevant downloaded images
4. organization context
5. explicit factuality instructions

Use Gemini's supported structured-output functionality and validate the response locally with Zod.

Do not scrape arbitrary text from the model response.

Define a structure similar to:

```ts
interface GeneratedArticle {
  title: string;
  slug: string;
  summary: string;
  body: string;
  metaDescription: string;
  tags: string[];
  imageAltTexts: string[];
  needsReview: boolean;
  warnings: string[];
}
```

The exact schema can be improved, but keep it small.

The body should be clean Markdown rather than arbitrary HTML.

Validate:

- title length
- slug format
- meta description
- required fields
- number of alt texts versus images
- body presence
- unexpected values

Gemini output must never be trusted merely because it conforms syntactically to JSON.

# 10. Gemini Editorial Rules

Create a clear reusable prompt inside the Gemini module.

The model is an editor, not a journalist inventing a story.

Its instructions must include rules equivalent to:

- Write a clear web article based only on supplied source material.
- Improve readability and provide useful context.
- Expand terse Instagram wording where possible without inventing facts.
- Never fabricate names.
- Never fabricate quotes.
- Never fabricate attendance figures.
- Never fabricate dates.
- Never fabricate locations.
- Never claim outcomes not present in the source material.
- Never identify people visible in photographs unless their identities were explicitly supplied.
- Do not infer sensitive characteristics about people.
- Do not state uncertain visual interpretations as facts.
- If information is unknown, omit it.
- Avoid generic AI filler.
- Avoid excessive promotional language.
- Avoid pretending firsthand knowledge.
- Do not mention that AI generated the article in the article body.
- Use the organization's actual name and location when supported by organization context.
- Produce descriptive but conservative image alt text.

A short Instagram caption should become a useful article, but article length must be dictated by the available information.

Do NOT force 1,000 words out of 30 words of source material.

A concise, accurate 250-word article is preferable to a fabricated 900-word article.

# 11. Review Safety Valve

Use `needsReview` and `warnings`.

Examples that should potentially trigger review:

- contradictory dates
- ambiguous location
- insufficient context
- uncertain event description
- malformed generated content
- unexpected media handling problem
- other factual uncertainty

Support an environment setting such as:

```text
AUTO_PUBLISH=true
```

When automatic publishing is enabled and the generated content passes validation with `needsReview === false`, publish normally.

If review is needed, save the article as a draft or otherwise exclude it from the production site while preserving the generated material for human inspection.

Do not discard it.

Document the review workflow.

# 22. Error Handling

Failures must be understandable.

Examples:

- Instagram authentication failure
- malformed Instagram response
- expired token
- failed media download
- Gemini API error
- Gemini schema validation failure
- image processing failure
- filesystem failure

Exit non-zero for meaningful CI failures.

Log enough context to troubleshoot without dumping tokens or sensitive API responses.
